01 — Motor Testbed · 2026

Edge-to-gateway motor control & telemetry testbed

Working · personal project · built solo · fall 2026

A DC motor I can start, stop and speed-control from a physical button and knob, or from my phone or laptop. An Arduino runs the motor, a Raspberry Pi 5 is the gateway, and a safety net shuts the motor off if the link to the Pi is lost.

2,000 ms

The fail-safe

The gateway sends the Arduino a steady heartbeat. If none arrives for 2,000 ms, the firmware stops the motor and locks into a fault state. Closing the browser tab, pressing Ctrl+C or killing the Python script all end the same way: motor off within the 2-second timeout. The physical button still works afterwards.

Problems I solved

  1. A1

    The knob and the web slider fought each other

    Two inputs wanted to set one speed, and electrical noise on the knob reading could look like a turn. I added a 35-count deadband, so the knob only takes over on a real turn and otherwise leaves the web setting alone.

  2. A2

    The motor had to stop if the computer side died

    I put the heartbeat timeout and fault lockout in the firmware instead of trusting the PC. The part that can fail is not the part responsible for stopping.

  3. A3

    A background tab tripped the safety net

    Browsers slow down timers in tabs you aren't looking at, so the heartbeat went quiet and the motor stopped. I moved the heartbeat tick into a Web Worker, which keeps its timing.

  4. A4

    The if/else chain kept growing

    I rewrote the firmware as an explicit state machine with switch/case. The behaviour became predictable and much easier to debug.

02 — SURE Research · Summer 2026

Jitter-aware perceptual deadband adaptation for haptic teleoperation over wireless networks

Kent State SURE program · 8 weeks, full-time · with a faculty advisor · proposal stage, no experimental results

In haptic teleoperation an operator feels forces from a remote robot, and that force data is streamed over a network. Perceptual deadband coding cuts the traffic by sending a new sample only when the change is big enough for a person to notice. Over wireless links, jitter (uneven packet timing) is a separate problem from delay, and it is rarely treated as a design target in the encoder. I proposed making the deadband threshold adapt to jitter measured in real time, so the sender backs off when the network gets unsteady. The summer's outcome was a formal research proposal, a background and methodology write-up, and an 8-week implementation roadmap that identifies this gap as a topic worth exploring.

03 — Project Sentinel · 2026

Computer-vision tracking prototype

Early learning build · completed · built solo

A Raspberry Pi 5 with a camera finds a colored object in the image and turns a servo so the camera follows it along one axis. I built it before I had touched Arduino, to learn the Pi, Linux and computer vision. It is a learning project, not a finished closed-loop controller.

How it works

  • Raspberry Pi 5 running headless, controlled over SSH.
  • An Arducam captures frames on a background thread, so the main loop always has the newest one.
  • OpenCV thresholds the image by color, picks the largest contour and computes its center point.
  • The horizontal distance from the image center drives an SG90 servo toward the target.

What I learned

  • Working on a headless Linux machine over SSH.
  • Basic image processing: thresholding, detection, centroids.
  • Lighting changes made the detected center jump; a tighter color range and averaging steadied it.
  • My first feedback loop: measure the error, move to reduce it.
